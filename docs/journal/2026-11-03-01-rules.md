# Rules

Date: 03.11.2026 · Task: 1.5 · Change: 1-5-rules

## Goal

Let the user write down once why a correspondence belongs to a project: a sender address, a domain or words
of the subject. A rule puts a chain into a project and a thread before the engine looks at it, both for new
chains after a mailbox read and on «Заполнить». The priority from the PRD and ADR 0030 is «вручную → правило
→ движок». The plan row is «Rules»; it was split off from task 1.4. With this task the stage «1. Project
trees» is done.

Before this task the only ways to place a chain were the engine and the user's hand; a user who knew that
all emails of one supplier belong to one project had to move every chain themselves.

## What was done

- Design session: the path was «new capability». The change `1-5-rules` got a proposal, delta specs, a
  design and tasks. The new capability `placement-rules` holds FR-43 (create a rule), FR-44 (list the rules)
  and FR-45 (edit and delete a rule). `chain-placement` gained FR-46 (place chains by rules) and modified
  FR-35, FR-36, FR-37, FR-39 and FR-42. `openspec validate --strict` passed and the user approved the
  deltas. Out of scope, sent to `docs/ideas.md`: applying a rule at once to chains already lying in a
  project, rules by recipient or text, «or»/«not» and a manual order, «Сделать правилом» from a chain page.
- Branch: the workspace branch was old and lacked tasks 1.3 and 1.4, so `feat/1-5-rules` was created from the
  fresh `main`.
- Schema: migration `0007` adds the table `placement_rules` and the columns `rule_condition` and
  `rule_value` to `chain_placements`. A placement of kind `rule` keeps a copy of the rule's condition and
  value, with no foreign key, so editing or deleting a rule never rewrites the explanation of a past
  placement.
- Matching: a rule matches a chain when an email of it came from the rule's address, domain or subdomain,
  or when each rule word begins a word of the first email's subject, case ignored, «ё» as «е». Priority is
  a full order: address, domain, subject words, then the earlier creation time, then the id; the list on the
  page shows the same order. Merge rank of placements: by hand or taken out, then rule, then engine.
- Backend: routes `GET`/`POST /rules`, `PUT`/`DELETE /rules/{id}` with the errors `rule_exists`,
  `too_many_rules`, `validation_failed`, `not_found`; `Placement` got the kind `"rule"` and the field
  `rule: {condition, value}`; `rule_placing.py` places chains by rules on a new chain and on «Заполнить»,
  where the placements of the project made by engine or by rules are recomputed and those by hand stay.
  The design «Interface» gained «Matching» (`RuleCondition`, `MatchRule`, `winning_rule`) because the unit
  tests call it.
- SPA: the page `/rules` («Правила») with a form, the list, «Изменить» and «Удалить» with the confirmation;
  the link sits in the links block of the start page (there is no separate header component);
  `placementLabel` shows «Правило · адрес …», «Правило · домен …» or «Правило · слова темы «…»».
- Tests were written before the code from the scenarios, in two sandbox cycles (backend groups 1 to 3, SPA
  group 4), each with a red check, an audit and `close`. All suites passed: 109 backend unit, 175 SPA and 284 database tests.
- Manual flows in a browser passed: (1) rules created and listed in priority order, with the lower-cased
  address, «Неразобранное», the delete confirmation, «Такое правило уже есть»; (2) «Заполнить» put «Акт
  скрытых работ» into «Акты» by subject words and Волков's chains into «Поставки» by address, a chain moved by
  hand stayed «Вручную» after the rule was retargeted; (3) adapted: `add-new` adds a reply to an existing
  chain, so a second account created the project «Сметы» and the rule «смета ремонт» before connecting the
  mailbox; the first read placed the chain by the rule into the unfilled project, and after deleting the rule
  it kept its «Правило» explanation. Test accounts were deleted from the dev database afterwards.
- Finish: the user decided to move rule CRUD out of `projects` into its own module
  `backend/app/modules/rules/` (see the decisions). The refactor used a `ProjectDirectory` of two callables
  injected by the router to avoid a circular import. Review fixes: rule create and update lock the user's
  projects before counting the 200 limit or checking the target (a race); reasons were added to the bare
  type-ignores in the tests; the limit message is built from `RULE_LIMIT`; the thread-by-name lookup runs in
  SQL with limit 1; the names lookup is filtered by the rules' project ids. The merged spec requirements
  FR-35 and FR-39 were shortened under openspec's 500-character limit without changing their meaning.
- Checks after finish: `just check` 17/17 PASS; tests 109 backend unit, 175 SPA, 284 database; `alembic
  check` shows no drift. The 44 warnings of the database suite are a pre-existing Alembic `path_separator`
  DeprecationWarning. The invariant review found no BLOCKER.
- Docs: ADRs 0063 to 0067; the guide `docs/guide/rules.md`; `docs/architecture.md`, `docs/domain.md`,
  `docs/prd.md`, `docs/plan.md` and `docs/ideas.md` updated; the change was archived as
  `openspec/changes/archive/2026-11-03-1-5-rules`.

## Mistakes and lessons

- The workspace branch was behind `main` again (no tasks 1.3 and 1.4), as in task 1.4. The AI created the
  branch from the fresh `main`, so no numbers went stale, but the cause is the same: check the branch
  against `main` first.
- The first design kept the rules inside `projects` and rejected a separate module with the reason «Отдельный
  модуль `rules` дал бы цикл импортов: правилу нужна проверка проекта, размещению нужны правила». The code-writer
  followed it and used the files `rules_router.py`, `rules_service.py`, `rules_repository.py` and
  `rule_schemas.py`, which reuse the fixed role names inside another module and so break `naming.md`. It was
  listed as a deviation in the handoff and caught only at finish; the user then chose a separate module, and
  the cycle was solved by injecting two callables (`ProjectDirectory`).- The first `rules` refactor was blocked: the code-writer could not write in the folder, because the
  worktree guard of the earlier finish session pointed at a different worktree. The code was left
  half-refactored and not importing until a session bound to this folder continued. Lesson: run `/finish`
  in the folder that holds the code.
- The race on the 200-rule limit (counting before locking the projects), bare `type: ignore` in tests and a
  limit message not built from the constant were found by the finish review, not by tests or checks.
- A lookup of project names with a limit of 200 would have raised `KeyError` for a user with more than 200
  projects; it was found by a doc-writer, not by the tests. A test with more than 200 projects would have
  caught it.
- Test defects found by the auditors before the code was accepted: the clock was not advanced between rule
  creations; engine keys were absent from the project descriptions, which made some tests vacuous; the
  absence of the thread «Акты» was not asserted; FR-42 date orders and a missing thread_name key case were
  not covered. Two tests failed on `close` because the `FakePlacementEngine` keys were not in the
  description «Ремонт офиса»; one SPA order test read the button text «Изменить Удалить» as part of a rule.
  The test-writer fixed all of them. The red check marks changed old test files PARTIAL (their unchanged
  scenarios pass without the code), so the auditor briefs had to be written by a scratchpad script that
  counts PARTIAL as red.
- The manual check showed the old form error «Такое правило уже есть» still above the form after a new
  submit with a field error. `RuleForm` now resets the mutation before each submit and the fix was checked by
  hand; no automated test covers it.
- Manual flows again hit the environment: the worktree had no `.env` (copied from the main checkout), Docker
  had no DNS so the frontend container could not download pnpm (a local Vite entry was added to
  `.claude/launch.json`), Vite listened only on `::1` while the browser used 127.0.0.1, and two
  `flow-checker`s hit their 40-turn limit, so the remaining steps were finished by hand in the browser. This
  is the same lesson as in task 1.4: a documented way to start the SPA without Docker in a worktree.
- Flow 3 as written could not run, because `just demo-mail add-new` adds a reply to an existing chain and not
  a new chain.
- The doc-writer broke some docstrings (E501 and a changed text in the OpenAPI) and three facts in the
  context of the ADRs 0063 to 0067 and the fact sheet were inaccurate; both were corrected after checks.
- Spec gaps, recommended to accept as they are, pending the user's decision at the finish question: clauses with no scenario of their own, all covered by tests (FR-43 value
  stripping and domain lower-casing, the 100 and 200 boundaries; FR-44 order within one kind; FR-45 changing
  the condition or value; FR-46 domain over subject words, a matching sender on a later email, «ё»; FR-42
  rule against rule).- Weak spots of old tests of tasks 1.3 and 1.4 were found by the auditors: FR-35 «Filling a project» checks
  only threads, not «Неразобранное»; FR-35 «Another user's project» uses an empty project; the FR-41 test in
  `test_placement_kept.py` lacks the new-email read; FR-37 engine percentages are not asserted in the
  backend. They are candidates for `docs/tech-debt.md`.

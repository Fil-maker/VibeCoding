# Application skeleton

Date: 23.10.2026 · Task: 0.1 · Change: 0-1-application-skeleton

## Goal

Task 0.1 «Application skeleton»: a FastAPI backend with a `health` module, a React SPA with a status page,
everything started in docker compose, plus `just` recipes and checks for both parts. It is a technical
change without requirements. Out of scope: sign-in, mail, analysis, a design system, deployment. No
product invariant is touched.

## What was done

- **Design session.** The change `0-1-application-skeleton` was opened on the branch
  `build/0-1-application-skeleton` with a proposal, a design with an «Interface» section, 19 tasks in five
  groups and a handoff marked `Approved: 2026-10-23`. The interface is `GET /api/v1/health` →
  `200 {"status": "ok", "database": "ok" | "unavailable"}` and the Russian UI texts of the status page.
- **Code session.** Two `code-writer` agents wrote code and tests in turn.
  - Backend: FastAPI app, the health endpoint, Alembic with an empty base migration, the OpenAPI schema
    exported to JSON; 8 unit tests and 2 database tests.
  - Frontend: Vite, React, strict TypeScript, the generated API client built by `just api-client`, the
    `HealthStatus` component; 5 Vitest tests.
  - Compose and commands: `docker-compose.yml`, recipes `just dev`, `just db`, `just test-db`,
    `just api-client`; a check in `just check` that the generated client is not stale; prek hooks for
    backend and frontend; `.claude/launch.json` for the preview.
  - Deviations from the briefs: TypeScript pinned to 6.0.3 and ESLint to 9.39.5, because typescript-eslint
    does not support TypeScript 6.1 and newer and `eslint-plugin-react` fails on ESLint 10.
  - Manual check through `flow-checker`: the page shows «Состояние сервиса», «Сервер: работает»,
    «База данных: доступна»; after `docker compose stop db` it shows «База данных: недоступна» and returns
    to «доступна» when the database starts.
- **`/finish` run.**
  - `just check` 17/17; tests backend 8, frontend 5, database 2. Alembic found no changes.
  - «Done when» verified in the browser, all three points met.
  - The invariant review found no blockers and 6 code findings, fixed by `code-writer` (a re-run was green):
    the database session dependency moved from the router to `get_database_session` in platform; the global
    `PLR2004` ignore removed; an upper bound added for pyright; a border-width token added; a reason
    comment added for `export default` in the ESLint config; route tests moved to `test_router.py`.
  - The user approved excluding `backend/migrations/versions` from ruff and pyright (files generated by
    Alembic); `config.md` requires explicit approval for any `exclude`.
  - The change was archived as `2026-10-23-0-1-application-skeleton`.
  - ADRs 0004–0007 were written in `docs/adr/` after confirmation; the planner proposed 13 doc portions, the
    main session grouped them into 4 (backend core, platform and health, frontend, infra and tooling), one
    `doc-writer` each, and the docs were checked by `doc-checker` agents, whose remarks were fixed; `just check` is green.

## Mistakes and lessons

- **The skill scripts did not run in two sessions.** In the first session `/feature` ran from a scratch
  folder, not the project, and `session_facts.py` was not found. In the second session the same commands
  were resolved relative to `openspec/changes/0-1-application-skeleton/` and `change_state.py` and
  `session_facts.py` were not found. Both sessions then continued. A check that the working directory is
  the project root before running a skill would have caught it.
- **A 502 on the very first request** during the manual check: the preview tab opened before the backend
  was up. The UI correctly showed «Сервер не отвечает». Waiting for the backend before opening the tab
  would avoid the noise.
- **The prek hooks for backend and frontend are skipped by `--all-files`** while those folders are not in
  git. With explicit `--files` all six hooks passed. Re-run them once the folders are committed.
- **The review caught what the code step had not:** a database session opened in the router, a global
  `PLR2004` ignore and an unbounded pyright version. The invariant review at `/finish` is what found them;
  none was found by the tests.
